01概要

目的

Box の同期対象フォルダ配下を階層構造を保ったまま Forma へ一括複製し、あわせて Box ID と Forma URN の対応表を構築する。

位置づけ

初期移行専用のレシピ。以降の同期は継続同期レシピ（Part 2）が担い、本レシピが作る対応表がその基盤になる。

観点扱い
1 案件あたりの実行1 回のみ。移行完了後はレシピを停止したまま保管する
案件をまたいだ利用テンプレートとして複数案件で流用する。案件ごとにレシピを複製し、設定値を差し替えて使用する（08 テンプレートとしての流用参照）
処理ロジック案件によらず共通。差し替えるのは接続先を指す値のみで、ステップ構成の変更は不要
なぜ対応表が必要か

Box でファイル名が変わっても Box の ID は変わらない。名前とパスだけで両システムを突き合わせる方式では、リネームを「別ファイルの新規作成」と誤認して重複を生む。ID 同士を紐付けておくことで、以降の同期で 1 件の検索だけで対応先を特定できる。

処理範囲

Forma のフォルダ URN をブラウザの URL からコピーしないこと。URL 上では %3A にエンコードされ、&viewModel=detail 等の余分なパラメータが付く。必ず Get folder in Autodesk Forma アクションの出力から取得し、urn:adsk.wipprod:fs.folder:co.xxxxx の形で使用する。

status の意味

04処理の仕組み

キュー方式による階層探索

Workato はレシピの再帰呼び出しを禁止しているため、フォルダ階層を再帰的に辿ることができない。そこで対応表そのものを作業キューとして兼用し、status = to_scan のフォルダが尽きるまでループを回す方式を採る。1 周ごとに 1 階層ずつ降りていくため、階層の深さを事前に知る必要がない。

周回処理対象この周で起きること
1 周目起点行（ルート）直下のファイルを転送し、直下のフォルダを to_scan で登録
2 周目1 階層目のフォルダ群同様に処理し、2 階層目を to_scan で登録
N 周目to_scan が 0 件IF が偽となり処理をスキップ、WHILE が偽となりループ終了

ステップの入れ子構造

  • 1トリガーHTTP Webhook（GET request）／実行はテストボタン
  • 2LUT起点行を検索
  • 3IF件数 = 0（起点行が無い）
    • 4LUT起点行を追加
  • 5REPEAT条件を満たす間繰り返す
    • 6LUTto_scan のフォルダを検索
    • 7IF件数 > 0
      • 8FOR EACHフォルダ単位のループ
        • 9Boxフォルダ内アイテムを一覧取得
        • 10FOR EACHアイテム単位のループ
          • 11待機1 秒（レート制限対策）
          • 12IFtype = folder
            • 13LUT登録済みか確認
            • 14IF未登録
              • 15Formaフォルダを作成
              • 16LUTto_scan で登録（キューに追加）
          • 17IFtype = file
            • 18LUT登録済みか確認
            • 19IF未登録
              • 20Boxファイル内容をダウンロード
              • 21Formaファイルをアップロード
              • 22LUTdone で登録
        • 23LUTこのフォルダを done に更新
    • 24WHILE件数 > 0 の間ループ継続
ステップ 23 の配置

ステップ 23 はアイテムのループ（10）の外側、フォルダのループ（8）の内側にある。「そのフォルダの全アイテムを処理し終えてから done にする」という順序を保証するため、この配置が必須となる。

重複チェックによる再開可能性

ステップ 13・18 で box_id の登録有無を確認し、未登録のときだけ作成・転送する。そのため中断しても対応表をリセットせず再実行すれば続きから再開できる。

再開時の例外

Forma への作成が成功した直後、対応表への登録前にジョブが停止した場合、Forma 側に対象が残るが対応表には行が無い状態になる。この状態で再実行すると 409 Conflict が発生する。該当オブジェクトを Forma 側で削除してから再実行すること。

07運用手順

実行前チェック

  1. 本番同期レシピを停止する（二重処理・レート制限の枠競合の防止）
  2. Forma 側の同期先フォルダを空にする。テストで作成したフォルダ・ファイルが残っていないか目視確認
  3. 対応表を全行削除する。起点行はステップ 3〜4 が自動生成するため手動投入は不要
  4. Box 側に 0 B のファイルが無いか確認する
  5. レシピを保存し、バージョン番号が更新されたことを確認する

実行

レシピエディタの「テスト」ボタンから実行する。Webhook トリガーのため、リクエストを送らない限りジョブは起きない。テスト実行でも Forma への作成・対応表への書き込みは本番同様に行われる。

1 回で完了しない場合がある

1 ジョブで Box ツリー全体を歩き切る設計だが、対象が多い場合は status=to_scan の行を残したまま終了することがある。その場合はもう一度実行すれば続きから処理される。to_scan が 0 件になるまで繰り返すこと。

実測では、フォルダ 7・ファイル 21（計 28 行）の構成で約 7 分・1 ジョブで完走している。

テンプレートとして保管する

運用方針

対応表（Lookup table）は案件ごとに専用のテーブルを作成する。全案件で 1 つのテーブルを共有する運用は採らない。

  • 100,000 行の上限を案件ごとに使える。共有すると全案件で 1 つの上限を分け合うことになる
  • 案件終了時にテーブルごと破棄できる

設計上の既知の課題

同名ファイルのアップロードは自動でバージョン追加にならない
  • Upload document は同名ファイルが存在すると 409 ERR_CONFLICT を返す
  • そのためファイル更新には別の処理経路が必要。これがフェーズ2 を分けている理由
  • 解決済み：File ID 欄を Enter file ID にして lineage 形式の ID を渡す（05 フェーズ2 の構成）
0 バイトのファイル

Upload object は File content が必須のため、0 バイトのファイルは転送できない。本レシピではステップ 4 の Size > 0 条件によりスキップする（エラーにはならない）。スキップされたことは記録に残らないため、必要であれば対応表に status = skipped_empty で登録する処理を追加する。
